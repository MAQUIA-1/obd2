# 웹 OBD 연동

## 현재 가능 범위

Web Serial 연결과 기본 11개 항목의 폴링·응답 해석을 `src/features/obd/`에 구현했다. 노트북 수집 코드의 기준은 `tools/obd_poll.py`의 TASKS, payload_for, decode다. [실차 수집 결과](Classic_폴링_수집_결과.md)와 [스마트폰 연결 순서](../../README.md#차량-연결)를 참고한다.

## 재현에 필요한 자료

- `tools/obd_poll.py`: ECU 송수신 헤더, 요청 명령, 초기화 순서, 요청 간격, ISO-TP 재조립, 항목별 해석식.
- `tools/can_capture.py`: Classic SPP 스트림 송수신 및 종료 처리. Linux BlueZ 구현. 브라우저의 대응 구현은 `src/features/obd/session.ts`에 있다.
- `research/fixtures/verified-poll-examples.json`: 기본 PID 9종의 실제 정상 응답·재조립 payload·해석 결과 각 1건. TypeScript 파서 테스트에서 기대값과 대조한다. 실차 정차 샘플로 실시간 데이터와 구분한다.
- `captures/poll-baseline-01/`: 전체 기본 수집 원본 107건 및 통계.
- `captures/poll-steering-02/`: 조향 조작 로그.
- `captures/body-controls-01`, `body-controls-03`, `body-options-04`, `body-lights-05`: 추가 옵션 조작 로그와 스냅샷.
- [추가 옵션 분석](추가옵션_분석_진행.md): 추가 옵션 후보와 공개 자료 적용 한계.

`captures/` 및 `research/sources/`는 .gitignore 대상이다. 다른 PC로 이동할 때 전체 폴더를 별도 복사하거나 백업한다. 최소 개발용 실제 응답 예제는 Git 제외 경로 밖인 `research/fixtures/`에 따로 복사해 두었다. 원시 로그 전체는 커밋 대상에 포함하지 않는다. Git 커밋과 별도로 원격 백업 여부를 확인해야 한다.

## 노트북에서 폴링 재현

Linux BlueZ와 Python의 `dbus`, `gi` 모듈을 사용한다. 차량을 정차한 상태에서 어댑터를 페어링하고 다른 앱의 연결을 해제한다. 아래 예제의 `$OBD_ADDRESS`에는 페어링한 어댑터 주소를 넣는다. 출력 경로는 수집 도구가 새로 만든다.

```sh
python3 tools/obd_poll.py --address "$OBD_ADDRESS" --seconds 20 --output captures/poll-baseline
```

조작 비교 시에는 안내와 실제 조작 확인 시각에 따로 마커를 남기고, 전환 구간을 제외해 비교한다. 수집 시각은 노트북에서 응답을 받은 시각이다. 방송 CAN 모니터링을 다시 조사할 경우 [첫 연결 기록](실차_첫연결_결과.md)과 [수집 도구](../../tools/can_capture.py)를 참고한다.

## 기본 요청표

| 항목 | TX / RX | 요청 |
|---|---|---|
| 속도 | 7E0 / 7E8 | 010D |
| RPM | 7E0 / 7E8 | 010C |
| 기어 | 7E1 / 7E9 | 21A0 |
| HV 전류·SOC·전압 | 7E4 / 7EC | 2101 |
| 조향각 | 7D4 / 7DC | 2101 |
| 냉각수온 | 7E0 / 7E8 | 0105 |
| 연료량 | 7E0 / 7E8 | 012F |
| 제어 모듈 전압 | 7E0 / 7E8 | 0142 |
| 외기온 | 7E0 / 7E8 | 0146 |

어댑터 초기화: ATD, ATE0, ATL0, ATS1, ATH1, ATD0, ATSP6, ATCAF1, ATAL. 각 명령의 OK와 완료 프롬프트를 확인한다. ECU가 바뀌면 ATSH로 TX 헤더를 바꾸고, 한 번에 하나의 요청만 보내 완료 프롬프트까지 읽는다. RX 헤더·서비스·PID·길이·ISO-TP 순서를 확인한 뒤 값을 적용한다. 명령이 3초 안에 끝나지 않거나 응답 경계를 잃으면 포트를 닫고 재연결을 기다린다. 종료 전의 요청과 다시 연결한 뒤의 요청은 서로 다른 세션에서 처리한다.

요청 간격은 [PID 설정](../../src/features/obd/protocol.ts)의 `interval`을 따르며 직전 응답 뒤부터 센다. 직렬로 한 요청씩 처리하므로 갱신 간격에는 응답 시간과 다른 PID 대기가 더해진다. R 수신 직후 조향각을 먼저 읽고, R이 유지되는 동안에는 조향각의 요청 간격을 700ms에서 300ms로 줄인다. 기어가 R을 벗어나거나 마지막 R 수신이 만료되면 조향각 요청을 700ms 간격으로 되돌린다. HV 전류·SOC·전압은 BMS 응답 하나에서 함께 읽고, 표준 PID는 각자 요청한다.

속도·RPM·기어·배터리·조향 값은 3초, 연료·냉각수온·제어 모듈 전압·외기온은 25초가 지나면 화면에서 만료된다. 브라우저는 차량 값을 메모리에 두고 연결을 종료하면 비운다.

연료량은 화면에 표시하기 전에 60초 시정수의 지수이동평균을 적용한다. 새 값의 반영 비율은 마지막 수신 이후 경과 시간으로 계산한다. 연결 후 첫 응답과 25초 넘게 수신이 끊긴 뒤 돌아온 응답은 새 기준값으로 사용한다.

## 추가 옵션의 상태

- 문 개폐: B005 데이터 byte 4 mask 0x04가 운전석 개폐에 대응·복귀. 다른 문과의 구분 미검증.
- 미등: B005 데이터 byte 4 mask 0x20, B00D 데이터 byte 4 mask 0x02가 OFF→미등→OFF에서 켜지고 복귀했다. 미등 전용인지 전체 등화/스위치 상태인지 미확정.
- byte 번호는 62 + DID 2바이트를 제거한 데이터의 0 기반 번호다.
- 깜빡이 미확인. 하향등·상향등은 이번 세션에서 사용자 ON 확인이 없으므로 검증 완료로 기록하지 않는다.
- 기본 기능 범위는 기존 항목으로 하고 추가 후보는 후속으로 남긴다.

## 남은 실차 검증

스마트폰 Chrome Web Serial → Classic SPP 연결, DeX 표시 및 연결 복구는 아직 실차 미검증이다. 노트북 BlueZ 성공을 브라우저 성공으로 대신할 수 없다. 정차 수집에서 속도·RPM은 0, 기어는 P였으며 동적 상태와 다른 기어는 이번 수집만으로 검증됐다고 할 수 없다.

Chromium의 모바일 화면에서 모의 Web Serial로 수신값 표시, 응답 분할, 오래된 값 숨김, 연결 해제, 재연결, 장치 이탈과 타임아웃을 확인했다. 목표 스마트폰·어댑터·DeX 구성에서 실제 포트 선택과 데이터 수신부터 확인한다.
