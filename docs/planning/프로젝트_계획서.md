# 구형 차량을 위한 스마트폰 기반 디지털 대시보드

React 프론트엔드 기말 텀프로젝트 계획서

- 작성일: 2026년 11월 19일
- 프로젝트명: OBD Dashboard (가칭)
- 개발 형태: 개인 프로젝트
- 문서 상태: 초기 계획안
- 일차 대상 차량: 2015년식 LF 쏘나타 하이브리드 (트림 확인 예정)
- 수집 방향: Bluetooth Classic SPP 연결 및 PID 폴링
- 기존 프로젝트: https://github.com/MAQUIA-1/obd-monitor

## 1. 기획 배경 및 개발 필요성

최근 차량의 통합 디스플레이에서 볼 수 있는 차량 정보 중심의 화면을, 디스플레이가 없는 구형 차량에서도 사용하고자 한다. 테슬라와 현대 플레오스의 대시보드 경험에서 아이디어를 얻되, 기존 차량에 스마트폰과 휴대용 모니터를 추가하는 방식으로 구현한다.

개발자는 이러한 필요에 따라 개인 차량용 OBD 모니터링 웹앱을 토이프로젝트로 제작한 경험이 있다. 이번 프로젝트에서는 기존 아이디어와 차량 연동 경험을 바탕으로 React 기반 프론트엔드를 새롭게 구성하고, 실제 표시 환경에 적합한 화면과 연결 상태 처리를 갖춘 서비스로 발전시키고자 한다.

실제 사용 구성은 삼성 스마트폰에서 웹앱을 실행하고, Samsung DeX를 활용하여 휴대용 모니터에 출력하는 방식이다. 스마트폰이 차량 데이터 수신과 화면 실행을 담당하며, 휴대용 모니터를 차량 정보 표시 장치로 사용한다.

본인이 필요로 하는 서비스는 차량의 여러 정보를 큰 화면에서 빠르게 확인할 수 있는 개인용 대시보드이다. 따라서 개발의 중심을 정보의 시인성, 화면 배치, 연결 상태의 명확한 표현, DeX 환경에서의 사용성에 둔다.

## 2. 프로젝트 목표

**차량 디스플레이가 없는 구형 차량에서, 스마트폰과 휴대용 모니터를 활용해 차량 정보를 한눈에 확인할 수 있는 React 기반 웹 대시보드를 구현한다.**

구체적인 목표는 다음과 같다.

1. OBD 어댑터로 수신한 차량 정보를 React 화면에 표시한다.
2. 휴대용 모니터의 세로 화면에서 주요 정보를 쉽게 읽을 수 있도록 구성한다.
3. 연결 중, 연결 해제, 데이터 미수신 등의 상태를 사용자가 구분할 수 있도록 한다.
4. 표시 항목과 테마를 설정하고 다음 실행 시 복원할 수 있도록 한다.
5. 차량이 없는 환경에서도 핵심 화면과 사용 흐름을 확인할 수 있는 데모 모드를 제공한다.

## 3. 대상 사용자 및 사용 환경

### 대상 사용자

- 차량 정보 표시용 디스플레이가 없는 구형 차량의 운전자
- 삼성 스마트폰과 휴대용 모니터를 활용해 차량용 디지털 대시보드를 구성하려는 사용자
- 일차적으로 개발자 본인의 차량과 OBD 어댑터를 사용하는 환경

### 사용 구성

```text
차량 ECU
   ↓ OBD 데이터
OBD/CAN 어댑터
   ↓ Bluetooth Classic SPP (RFCOMM)
삼성 스마트폰의 Chrome 웹 브라우저 (Web Serial)
   ↓ Samsung DeX를 통한 화면 출력
휴대용 모니터의 차량 대시보드
```

일차 대상은 LF 쏘나타 하이브리드다. Bluetooth Classic SPP를 첫 연결 방식으로 선택하며, 어댑터의 실제 SPP 서비스 제공 여부와 Android Chrome의 Web Serial RFCOMM 동작을 확인한다. DeX 출력 상태에서 연결 유지 및 브라우저 동작도 함께 검증한다. SPP가 없거나 실제 장애가 확인된 경우에 BLE 등 대안을 검토한다. 두 연결 방식을 처음부터 모두 구현하거나 비교하지 않는다. 정확한 차량 연식·트림, 어댑터 모델, 스마트폰, 브라우저, 모니터 해상도는 확인 후 보고서에 기록한다.

## 4. 주요 사용 시나리오

1. 사용자가 스마트폰을 휴대용 모니터에 연결하고 DeX에서 웹앱을 실행한다.
2. 웹앱에서 연결 버튼을 눌러 OBD 어댑터를 선택한다.
3. 연결 및 초기화가 완료되면 차량에서 수신되는 정보가 대시보드에 표시된다.
4. 사용자는 표시 항목과 주간·야간 테마를 설정한다.
5. 연결이 끊기거나 데이터 수신이 중단되면 화면에서 해당 상태를 확인하고 다시 연결한다.

발표 및 개발 환경에서는 데모 모드를 선택하여 샘플 데이터가 표시되는 대시보드를 확인한다. 데모 화면에는 실제 차량 연결과 구분되는 표시를 유지한다.

## 5. 기능 범위

### 필수 구현 기능

| 기능 | 구현 내용 | 완료 기준 |
|---|---|---|
| 차량 연결 | Web Serial을 통한 Classic SPP OBD 어댑터 선택 및 연결, 초기화, 연결 해제 | 대상 장치에서 연결 후 데이터 수신 가능 |
| 실시간 대시보드 | 속도·RPM 등 주요 차량 정보를 읽기 쉬운 형태로 표시 | 실제 수신값이 단위와 함께 갱신됨 |
| 상태 안내 | 연결 대기·연결 중·연결 완료·실패·해제 상태 표시 | 현재 상태와 필요한 조작을 확인할 수 있음 |
| 데이터 유효성 표시 | 미지원 항목, 미수신 값, 갱신이 중단된 값 구분 | 이전 값이나 미수신 값을 현재 정상값으로 오인하지 않음 |
| 표시 설정 | 보조 표시 항목 선택 및 주간·야간 테마 변경 | 설정이 화면에 적용되고 새로고침 후 복원됨 |
| DeX 화면 대응 | 휴대용 모니터의 세로 화면에 맞는 배치와 크기 조정 | 실제 대상 해상도에서 잘림과 겹침 없이 사용 가능 |
| 데모 모드 | 샘플 데이터를 이용한 대시보드 동작 | 차량 없이 핵심 화면과 설정 기능 시연 가능 |

### 차량 정보 표시 후보

- 주요 정보: 속도, 엔진 RPM, 기어 P/R/N/D/M, 조향각, 하이브리드 READY
- 보조 정보: 연료량, 냉각수 온도, 12V 전압, 외기 온도
- 차량별 추가 정보: 배터리 SOC, 고전압 배터리 전압·전류, 조향각

표시 항목은 대상 차량에서 실제로 수신하고 의미를 검증할 수 있는 CAN 신호 또는 PID를 확인한 후 확정한다. 차량별 전용 정의가 필요한 정보는 지원 범위를 명시하며, 모든 차량에서 동일하게 제공된다고 가정하지 않는다. 추가 후보와 분석 결과는 [실차 추가 신호 조사](../vehicle/추가옵션_분석_진행.md)에 정리한다.

현재 개발 경로는 Classic SPP 기반 PID 폴링이다. 실차에서 Classic 연결과 속도·RPM 각 1회 조회가 정상 응답했고, 수동 모니터에서는 방송 프레임을 확보하지 못한 결과를 바탕으로 사용자가 이 방향을 선택했다. 필요한 ECU/PID를 순차 요청하고 변화 속도에 따라 우선순위와 요청 간격을 조정한다. 지속 폴링의 성능과 다른 항목의 수신은 추가 검증한다. 스니핑과 내부 CAN 접속 경로 연구는 별도 후속 과제로 남긴다.

공개 자료는 LF 전용으로 한정하지 않고 현대·기아 일반 CAN, LF 일반형, 옵티마 HEV/PHEV, 아이오닉·니로 HEV 등으로 넓게 조사한다. 같은 캡처에 여러 해석 정의를 적용하고 실차 조작으로 맞는 후보를 검증한다. 기존 정의로 해석되지 않는 핵심 항목만 역분석한다. 방송 메시지용 DBC와 요청·응답용 PID를 구분하여 적용하며, 차종별 PID를 무차별 요청하는 방식은 사용하지 않는다. 자료와 적용 순서는 [현대·기아 CAN 리서치](../vehicle/현대_기아_CAN_리서치.md)에 정리한다.

### 여유가 있을 때 검토할 기능

- 사용자가 선택할 수 있는 복수의 대시보드 배치
- 최근 수신값의 짧은 추세 그래프
- 화면 전체 표시 및 실행 편의 기능

### 이번 프로젝트에서 제외할 범위

회원가입, 서버 기반 사용자 관리, 주행 기록 분석 서비스, AI 차량 진단, 내비게이션, 차량 제어 기능은 초기 개발 범위에 포함하지 않는다. 순정 계기판을 대체하는 인증 장치가 아닌 보조 정보 표시용 웹앱으로 개발한다.

## 6. 화면 구성 및 디자인 방향

화면은 실제 모니터에서 읽기 쉬운 정보 중심으로 구성한다. 차량 인포테인먼트 화면의 큰 정보 배치와 일관된 시각 체계를 참고하되, 브랜드 화면을 그대로 복제하지 않고 본 프로젝트의 표시 항목과 사용 환경에 맞게 설계한다.

| 화면 | 주요 구성 |
|---|---|
| 시작 및 연결 화면 | 서비스 설명, 차량 연결 버튼, 데모 시작 버튼, 연결 진행 및 오류 안내 |
| 대시보드 | 속도·RPM 중심 영역, 보조 정보 영역, 연결 및 수신 상태, 설정 진입 |
| 설정 화면 또는 패널 | 표시할 보조 항목, 주간·야간 테마, 연결 관리 |

디자인 원칙은 다음과 같다.

- 주요 수치와 단위를 명확한 크기와 대비로 표시한다.
- 숫자 변화로 주변 배치가 흔들리지 않도록 구성한다.
- 색상과 텍스트를 함께 사용해 연결 상태와 데이터 상태를 전달한다.
- 장식 효과와 불필요한 애니메이션을 줄이고 정보의 가독성을 우선한다.
- 설정과 연결 조작은 정차 상태에서 수행하는 흐름으로 설계한다.

## 7. 기술 구성 및 코드 설계

다음 구성을 초기안으로 사용하며, 장치 연동 검증 결과에 따라 세부 구현을 조정한다.

| 구분 | 계획 |
|---|---|
| 프론트엔드 | React, TypeScript, Vite |
| 차량 통신 | Web Serial 기반 Classic SPP, 어댑터 초기화·순차 PID 요청·응답 검증·항목별 수신 상태 관리 |
| 상태 관리 | React 상태와 Context 또는 사용자 정의 Hook |
| 로컬 저장 | localStorage를 이용한 표시 설정 저장 |
| 개발·발표 데이터 | 실제 데이터와 동일한 형식으로 공급하는 데모 데이터 모듈 |
| 소스 관리 | GitHub 저장소, 실행 방법과 지원 환경을 포함한 README |

통신 처리, CAN 신호 및 PID 해석, 데이터 상태, 화면 컴포넌트를 분리하여 관리한다. 대시보드는 공통 데이터 형식을 사용하고, 실제 차량 데이터와 데모 데이터의 공급 경로를 분리한다. 연결 해제 시 수신 처리와 타이머를 정리하고 화면 상태를 갱신한다.

기존 프로젝트에서 참고하거나 재사용한 코드와 이번 과제에서 새로 작성한 부분은 보고서에 구분하여 기록한다. 실제 재사용 범위는 기존 소스를 검토한 후 결정한다.

## 8. 개발 순서 및 검증 계획

제출일이 확정되지 않았으므로 날짜 대신 단계별 완료 기준으로 관리한다.

| 단계 | 주요 작업 | 완료 기준 |
|---|---|---|
| 1. 요구사항 및 장치 검증 | 공개 정의 조사, SPP 지원 확인, 노트북에서 주요 PID 폴링 검증, 스마트폰 Chrome 및 DeX의 Web Serial 연결 확인 | 실제 연동 가능 여부와 표시 항목 확정 |
| 2. 화면 설계 | 주요 정보의 우선순위 결정, 대상 해상도 기준 화면 배치 | 화면 구성과 필수 기능 범위 확정 |
| 3. React 화면 구현 | 공통 컴포넌트, 대시보드, 설정, 데모 데이터 구현 | 데모 모드에서 전체 사용 흐름 동작 |
| 4. 실제 차량 연동 | 검증된 CAN 신호 또는 PID 해석 연결, 데이터 상태 처리 | 실제 차량에서 주요 정보 표시 |
| 5. 사용성 및 오류 검증 | DeX 출력, 연결 실패·해제, 미수신 값, 설정 복원 확인 | 필수 기능의 완료 기준 충족 |
| 6. 제출 및 발표 준비 | GitHub 정리, PDF 문서 작성, 시연 영상·발표 자료 준비 | 재현 가능한 소스와 제출물 완성 |

CAN 신호는 공개 DBC의 ID·길이·비트 위치·단위·열거값과 실제 상태를 대조하고, 대안 정의의 결과를 분리한다. PID 해석은 확보한 응답 예시와 기대값을 대조한다. 실제 차량 시험에서는 수신값 표시와 지원 항목을 확인하고, 데모 시험에서는 화면과 설정 흐름을 확인한다. 실제 시험 결과와 데모 확인 결과는 보고서에서 구분한다. 초기 차량 연동 검증 및 촬영은 정차 상태에서 진행하며, 속도 등 주행이 필요한 항목은 별도 절차를 마련한다.

| 예상 문제 | 대응 계획 |
|---|---|
| 어댑터의 SPP 미지원 또는 DeX에서 Web Serial 연동 제한 | 선택한 Classic 경로를 먼저 검증하고 실제 제약이 확인된 경우에 BLE 등 대안 검토 |
| 차량 또는 어댑터별 PID 차이 | 본인 차량을 우선 지원하고 지원 항목 및 전용 PID 의존성 명시 |
| 방송 수신량 증가·버퍼 초과·갱신 지연 | 필요한 CAN ID 필터링과 처리량 확인, PID 대안에서는 요청 주기 조정 |
| 연결 해제 후 이전 수치가 남는 문제 | 수신 시각을 관리하고 오래된 값과 연결 해제를 명시적으로 표시 |
| 발표 장소에서 실제 차량 연결 불가 | 데모 모드와 사전 촬영한 실제 연결 영상 준비 |
| 구현 범위 확대에 따른 완성도 저하 | 필수 기능을 먼저 완료하고 선택 기능은 이후 검토 |

## 11. 기대 효과 및 최종 완료 기준

본 프로젝트는 개발자가 실제로 필요로 했던 차량 정보 표시 환경을 React 웹 서비스로 구현하는 데 의의가 있다. 프론트엔드 화면 설계와 상태 관리뿐 아니라 외부 장치에서 들어오는 비동기 데이터, 연결 오류, 데이터 유효성을 다루는 경험을 얻을 수 있다.

최종 완료 기준은 **대상 차량에서 수신한 주요 정보가 DeX에 연결한 휴대용 모니터에 정상적으로 표시되고, 연결 상태 및 표시 설정을 사용할 수 있으며, 차량이 없는 평가 환경에서도 데모로 핵심 기능을 재현할 수 있는 것**이다. 계획서와 결과 보고서에는 실제 구현 범위와 검증 근거를 일치시켜 작성한다.

## 12. 모바일 웹 연결 확인 사항

2026-11-19 확인한 Chrome 공식 138 릴리스 문서에는 Android의 Web Serial over Bluetooth RFCOMM 지원이 명시되어 있다. 삼성 스마트폰의 Chrome을 일차 지원 브라우저로 하고 HTTPS로 제공한다. Android에서 스캐너를 페어링한 뒤 웹앱 연결 버튼에서 사용자가 포트를 선택하도록 구성한다. 노트북의 Classic 연결 성공은 확인됐지만 스마트폰·DeX에서의 실제 연결, 지속 수신, 화면 꺼짐·백그라운드 복귀는 아직 검증하지 않았다.

브라우저 API 지원 확인 → 포트 선택 → ATI 식별 → 속도 PID 1회 조회 → 짧은 연속 폴링 순으로 검증한다. Chrome과 다른 모바일 브라우저 및 앱 내 WebView를 동일하게 지원한다고 가정하지 않는다. 스마트폰 시험 시 노트북의 스캐너 연결은 종료한다.

- Android 지원 근거: https://developer.chrome.com/release-notes/138/
- 포트 선택 및 사용자 동작: https://developer.chrome.com/docs/capabilities/serial

### 실차 폴링 초기 검증 결과

Classic으로 주요 PID 9종을 약 20초 조회해 107건 모두 응답 형식 검증을 통과했고, 기본 화면 항목 11개를 확보했다. 조향은 사용자 중앙·좌측 조작과 수치 변화가 대응함을 확인했으며 추가 반복 시험은 사용자 요청으로 중단했다. 실제 요청 간격과 추가 후보, 남은 검증 범위는 [수집 결과](../vehicle/Classic_폴링_수집_결과.md)에 정리한다. 장시간 안정성 및 모바일·DeX 연결이 검증됐다는 뜻은 아니다.
